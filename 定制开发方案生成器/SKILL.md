# 定制开发方案生成器

> 一个面向**企业微信定制开发服务商**的方案生成 Skill。**不预设服务商、客户、行业、场景**——但**平台始终锁定企业微信生态**。服务商可以是 A 公司、B 公司；客户可以是任意行业、任意公司、任意场景；而承载需求的，永远是企业微信的智能表格、智能机器人、企业自建应用、微盘、工作台等原生能力。

## 平台铁律：只用企业微信生态（绝对不能违反）

> 我们是**企业微信定制开发服务商**。所有交付物——HTML 方案、docx、xlsx、搭建 Prompt——**必须且只能**基于企业微信生态的能力来承载需求。

| ✅ 必须用（企业微信生态） | ❌ 绝对禁止出现（友商平台） |
|---|---|
| 企业微信**智能表格** | 钉钉、钉钉宜搭 |
| 企业微信**智能机器人** / 群机器人 | 飞书、飞书多维表格、Lark Base |
| 企业微信**自建应用** / 工作台 | 腾讯文档以外的第三方文档 |
| 企业微信**审批 / 汇报 / 日程** | Notion、Airtable、简道云、明道云等 |
| 企业微信**微盘**（附件/容量） | 任何其他低代码/SaaS 平台 |
| 企业微信**OCR / 通讯录 / 消息推送** | — |

- 写"搭建步骤"时，菜单路径只能是企业微信的真实路径（如「应用 → 智能表格」）
- 写"自动化/提醒"时，只能是企业微信智能表格自动化、群机器人 webhook、应用消息推送
- 写"AI 能力"时，指企业微信的智能机器人（对内办公、知识库问答），不写外部大模型平台
- **如果客户原话提到了钉钉/飞书**：在 docx「⚠️ 待确认」里记录，但方案主体仍按企业微信落地，并说明迁移建议

## 核心原则：去角色化（但平台不在去角色化范围内）

> 这是本 Skill 第二核心的设计原则，**绝对不能违反**。

| 维度 | 是否预设 |
|---|---|
| **服务商是谁** | 不预设。可能材料里会提到"杭州装企云"，也可能没提到；可能这次服务商是甲方内部团队 |
| **客户是谁** | 不预设。可能是"亿选装饰"，也可能是"城邦美商"，也可能是内部项目 |
| **行业是什么** | 不预设。可能这次是家装，下次是外贸，再下次是医疗 |
| **场景是什么** | 不预设。可能是数据分析、订单管理、巡店、CRM、HR、报销…… |
| **使用平台** | ⚠️ **预设且锁定 = 企业微信生态**。智能表格 / 智能机器人 / 自建应用 / 微盘 / 工作台，不接受钉钉/飞书 |

**AI 怎么知道这些信息？** —— 服务商/客户/行业/场景**从输入材料里抽取**，抽不到标"⚠️ 待确认"；**平台无需抽取，恒定为企业微信**。

## 适用场景

用户在以下任一情况时，必须调用本 Skill：

1. 提供 **1 份或多份材料**（docx/doc/pdf/md/txt），希望生成对外可交付的方案包
2. 明确要求"可视化方案 / 方案 HTML / 需求确认表 / 智能表格 demo / 搭建 Prompt"
3. 提到"按之前那种格式再来一份"或类似指代
4. 一次性提供"需求 + 知识库 + 服务商需求描述 + 范例"中的多类材料

## 输入材料识别（4 类）

Skill 必须能从一堆文件里**自动识别**每份是什么类型：

| 类型 | 文件名特征 | 抽取内容 |
|---|---|---|
| **A. 知识库** | 路径含 `knowledge_*/`、标题含"行业" | 行业术语、流程节点、角色定义、典型痛点 |
| **B. 需求沟通记录** | 路径含 `requirement_*/`、标题含"沟通记录"或"第 N 题" | 客户名、服务商名、痛点、场景、关键诉求 |
| **C. 服务商需求描述** | 标题含"服务商需求" | 服务商视角对客户需求的解读、自己的方案设计思路 |
| **D. 结果范例**（可选） | 路径含 `result_*/` | 风格参考、输出格式参考 |

**识别优先级**：B > C > A > D
- B（沟通记录）通常最权威
- C 是服务商视角的二次解读
- A 提供行业背景知识
- D 仅作风格参考

> ⚠️ **知识库错配警告（必读）**：A（知识库）的标题/行业**可能与本次真实需求完全无关**。例如曾出现挂着"金融服务/助贷"知识库、实际却是"固定资产管理"的用例。
> - **永远以 B（沟通记录）判定真实场景**，A 仅在确实同主题时才参考；主题不符就**直接弃用 A**。
> - 绝不能把错配知识库的术语/表结构（如"订单/三向资金"）硬套到真实场景上。
> - 当判断发生错配时，在搭建 Prompt 的"注意事项"里显式写一句："不要使用 {错配行业} 知识生成本项目表结构；本项目是 {真实场景}。"

## 三/四件套交付物

按材料完整度产出 3-4 份文件，输出到 `/workspace/{客户名简称}/`：

| 序号 | 类型 | 文件名规范 | 主要受众 |
|---|---|---|---|
| ① | 可视化方案 | `{客户名简称}_{行业}_{场景}_可视化方案_V{版本}.html` | 客户决策层 |
| ② | 正式方案 docx | `{客户名简称}_需求确认与方案设计表_V{版本}.docx` | 客户业务/IT 部门 |
| ③ | 智能表格 demo | `{客户名}_{场景}_{工具名}_V{版本}.xlsx` | 客户一线使用方 |
| ④ | 搭建 Prompt | `{客户名简称}_智能表格搭建Prompt.md` | 客户/实施团队（教他们怎么搭） |

> **第 ④ 份是新增的**。当 Skill 判断用户最终需要"在真实平台搭建"时（如企业微信智能表格），必须额外输出第 ④ 份，告诉用户具体步骤、字段配置、权限设置。

## 服务商信息配置

**可选配置** `rules/服务商信息.md`（首次使用前可创建）：

```markdown
# 当前服务商信息（可选）
- 服务商名称：{如：杭州装企云网络科技有限公司}
- 联系电话：{如：138-XXXX-XXXX}
- 邮箱：{如：contact@example.com}
```

**重要**：
- 如果本次输入材料的 B（沟通记录）里已经提到服务商，**以 B 里的为准**
- 如果 B 没提但 C（服务商需求描述）里提到了，**以 C 里的为准**
- 都没提，**使用占位符 `[服务商名称待填]`**，禁止编造
- **永远不要把"默认服务商"硬编码到 Skill 里**

## 标准工作流（7 步）

### Step 1: 识别并分类输入材料
- 扫描所有提供的文件路径和标题
- 归类为 A/B/C/D 四类
- 如果某类材料缺失，标记"⚠️ 缺失"并启用对应兜底策略

### Step 2: 解析输入材料
- 从 B（沟通记录）抽取：客户名、行业、痛点、场景、关键角色
- 从 C（需求描述）抽取：服务商视角的方案思路
- 从 A（知识库）抽取：行业术语、流程节点、典型角色
- 与 `rules/输入解析规则.md` 交叉验证
- **缺失的关键信息必须标"⚠️ 待确认"，不编造**

### Step 3: 加载生成规则与可复用 Prompt
- HTML 规则 → `rules/html生成规则.md`；**可复用生成 Prompt → `prompts/html生成Prompt.md`**
- Word 规则 → `rules/word生成规则.md`；**可复用生成 Prompt → `prompts/docx生成Prompt.md`**
- Xlsx → `rules/xlsx生成规则.md`
- 通用设计 → `rules/设计规范.md`
- 行业术语 → `rules/行业术语库.md`

> **`prompts/` 是"可直接执行的生成提示词"**，把已解析的需求要点填进去即可产出对应交付物。规则文件讲"结构与样式标准"，Prompt 文件讲"怎么一步步生成"，两者配合使用。

**docx 结构选择**：默认用 **11 节《需求确认与方案设计表》主结构**（确认表式、可签署、界定边界，福鸿/鹏宁担保为基准）；仅当客户明确只要一份"概览方案书"时才用 10 章轻量结构。

**HTML 叙事选择**：先判断 **A 营销式**（方案已定、打动决策层）还是 **B 咨询诊断式**（需求梳理、先诊断后开方），积分激励/流程重构/资金协同类优先 B。

### Step 4: 判断场景类型
Skill 必须先判断本次需求属于**哪种场景类型**（按需扩展）：

| 场景类型 | 典型特征 | 模板选择 |
|---|---|---|
| **数据分析** | 涉及"数据看板/报表/BI/数据可视化/数据驾驶舱" | 数据分析模板（KPI 大屏 + 多维分析） |
| **流程协同** | 涉及"审批流/工单/订单/打样/巡检" | 流程协同模板（流程图 + 状态机 + 角色泳道） |
| **客户/销售管理** | 涉及"CRM/客户档案/商机/销售漏斗" | CRM 模板（客户主数据 + 销售流程） |
| **人力/行政** | 涉及"HR/招聘/考勤/报销/培训" | HR 模板（人员主数据 + 流程） |
| **积分/激励** | 涉及"积分/改善提报/奖励/兑换/排行榜/库存闭环" | 积分激励模板（**多表关联汇总** + 积分账户 + 奖品库存） |
| **资产/台账管理** | 涉及"固定资产/设备/盘点/折旧/领用/借调/调拨/报废" | 资产管理模板（台账主表 + 折旧公式链 + 流转留痕 + 报废下账闭环） |
| **通用兜底** | 上述都不像 | 通用业务模板 |

> 场景类型决定了 HTML 的章节侧重、xlsx 的 Sheet 列表、docx 的痛点描述角度。
> **积分/激励** 是"人力/行政"下的特殊子类型，核心是**跨表关联**（见下方设计原则），范例见 `examples/福鸿客户/`。
> **资产/台账管理** 也属"人力/行政"子类型，核心是**折旧公式链 + 状态驱动流转留痕 + 报废下账闭环**（见 `rules/xlsx生成规则.md`），范例见 `examples/贵州宏立城/`。

### 跨表关联设计原则（积分激励 / 库存闭环类场景必用）

当场景出现"积分自动累计""库存自动增减""排行榜汇总"等需求时，**单表设计不够**，必须用**多表 + 关联字段**实现自动汇总：

| 关联方式 | 用途 | 例子 |
|---|---|---|
| **lookup（查找引用）** | 从关联表带出某字段值 | 提报表选了"提报人"，自动带出其"部门" |
| **rollup（汇总计算）** | 按关联把多条记录 sum/count 到主表 | 把某员工所有"已落实"提报的积分 sum 到人员积分表 |
| **公式字段** | 表内字段间计算 | 可用积分 = 累计积分 − 已用积分 |

**设计步骤**：
1. 先画"实体关系图"——哪些是主数据表（人员、奖品），哪些是流水表（提报、领取、入库）
2. 列出"自动汇总需求"——哪个数字需要被自动算出来（累计积分、已用积分、当前库存）
3. 为每个汇总需求指定：源表 → 关联字段 → 汇总方式 → 目标表字段
4. 在 docx / 搭建 Prompt 里**必须出现"表间关联关系"表**，逐条写清 6 要素：主表 / 关联表 / 关联字段 / 汇总方式 / 自动带出内容 / 目的

#### 进阶范式：三层表结构 + 资金三态闭环（对多方结算类场景）

当场景涉及"对多方（银行/经销商/员工…）的应收应付结算"时，用**三层表结构**组织：

| 层 | 角色 | 例子 |
|---|---|---|
| **业务主表** | 承载一笔业务全生命周期 + 各方应收应付金额字段 | 订单管理（含银行应收、供应商提成、员工提成） |
| **基础数据库** | 被主表关联选择，并被回写汇总业绩/应付 | 贷款产品库、经销商库、员工库 |
| **流水明细表** | 记录每一笔实际收/付款，回写基础库 | 银行收款、经销商付款、员工提成下发 |

**资金三态通用公式**（任何对多方结算都可套用）：
```
应付/应收（业务主表按对象 rollup）
  − 已付/已收（流水明细表按对象 rollup）
  = 待付/待收（基础库公式字段）
```
范例见 `examples/广州鹏宁担保/`（金融助贷，银行/经销商/员工三向资金协同）。

### Step 5: 调用范例
- 参考 `examples/` 下的完整四件套，校准风格与深度
- 范例按"场景类型"分类管理

### Step 6: 生成三/四件套
- 严格按"三件套一致性"原则
- **平台只用企业微信生态**：智能表格/智能机器人/自建应用/微盘/工作台，绝不出现钉钉/飞书
- **第 ④ 份 Prompt 文件**对"数据分析""流程协同""客户/销售""积分/激励"等需要在企业微信内搭建的场景生成
- **积分/激励等含跨表关联的场景**：docx 与第 ④ 份必须包含"表间关联关系"表与"一期/二期范围划分"

### Step 7: 自检清单
- [ ] 三/四件套的客户名、版本号、行业、核心场景表述完全一致
- [ ] 至少有 3 个**量化价值点**
- [ ] 流程图覆盖**端到端**（如适用）
- [ ] 智能表格字段与 docx 功能清单**一一对应**
- [ ] 所有"待确认"项已在 docx 中以"⚠️ 待确认"高亮
- [ ] **没有凭空编造服务商名、客户名、联系方式**
- [ ] **四件套中没有出现钉钉、飞书等任何友商平台**；所有承载能力均为企业微信生态
- [ ] 搭建步骤里的菜单路径都是企业微信真实路径

## 三件套一致性原则

1. **字段对齐**：docx 功能清单 ↔ xlsx 字段
2. **流程对齐**：HTML 流程图 ↔ docx 流程章节 ↔ xlsx 状态字段
3. **数字对齐**：所有量化指标在 3 处出现的数字必须相同
4. **角色对齐**：所有参与角色称谓统一
5. **版本对齐**：三件套版本号必须同步
6. **服务商对齐**：所有文档中的服务商名必须相同

## 一期边界克制原则（售前必守）

客户在沟通中常会顺口提出"额外需求"（如宏立城客户提到"后续想把用车/用章/会议室审批也搬线上"）。**不要照单全收塞进一期**：

- **聚焦客户明确的主诉求**做一期，额外需求一律推到"二期扩展"或"暂不建议"
- 在 HTML 用"一期必做 / 二期扩展 / 暂不建议"三栏、docx 第二节用"方案边界"表把范围白纸黑字框死
- 报价模块表里二期模块标"否，二期，另行评估"，避免客户误以为都包含在本次费用里
- 这既控制交付风险，又给二期留出商机——是专业服务商的标志，不是偷懒

## 反例（绝对禁止）

- ❌ 在文档里硬编码"闪鱼""泽哥"或任何特定公司名
- ❌ 凭空编造客户没有提到过的数据
- ❌ 用客户原文没出现的术语
- ❌ 把"默认服务商"写死到模板里
- ❌ 跳过 Step 1 直接生成
- ❌ 在 docx 里用 HTML 标签
- ❌ **认为"杭州装企云就是默认服务商"**——它只是这次的特殊例子
- ❌ **认为"家装/外贸/餐饮"是默认行业**——它只是这次的输入
- ❌ **在任何交付物里出现钉钉、飞书、宜搭、多维表格、Lark、Notion、Airtable、简道云等友商平台**
- ❌ 把"使用平台"当成可变的、需要从材料抽取的维度——平台恒定为企业微信
- ❌ 写"在企微/钉钉/飞书里搭建"这种含糊措辞——只写企业微信
- ❌ **把客户顺口提的额外需求全塞进一期**——该推二期的要克制地推二期

## 失败兜底

| 缺失项 | 兜底策略 |
|---|---|
| 服务商信息缺失 | 使用 `[服务商名称待填]` 占位符，docx 顶部加 ⚠️ 提示 |
| 输入材料不完整 | 仍生成三件套，但 docx 顶部必须包含"⚠️ 缺失材料清单" |
| 客户名不明确 | 用"客户"占位，并标注待确认 |
| 行业不明确 | 用"通用"行业模板，仍可交付 |
| 完全没有行业知识库 | 退化为通用业务模板，仍可交付 |

## 范例与脚本

- 范例：`examples/{客户名}/` 存放历史成功案例
  - `examples/城邦美商/` — 服装外贸 / 打样及订单场景（流程协同类）
  - `examples/海岸咖啡/` — 连锁餐饮 / 巡店管理场景（流程协同类）
  - `examples/亿选装饰/` — 家装 / 前端数据分析场景（数据分析类，**带第 ④ 份 Prompt**）
  - `examples/福鸿客户/` — 制造业 / 改善提报积分激励场景（积分激励类，**跨表关联 + 咨询诊断式 HTML + 第 ④ 份 Prompt**）
  - `examples/广州鹏宁担保/` — 金融担保 / 助贷订单管理场景（流程协同+资金闭环类，**三层表结构 + 资金三态闭环 + 咨询诊断式 HTML + 第 ④ 份 Prompt**）
  - `examples/贵州宏立城/` — 行政 / 固定资产盘点与折旧管理场景（资产/台账类，**折旧公式链 + 状态驱动流转留痕 + 报废下账闭环 + 咨询诊断式 HTML**；知识库错配的典型样本）
- 脚本：`scripts/` 提供可独立运行的 Python 生成脚本
  - `init_new_client.py` 一键初始化新客户
  - 改 CONFIG 块就能换客户
  - 每份脚本有两个版本：`generate_xxx.py`（通用模板）和 `generate_xxx_{客户名}.py`（已配置好具体客户的实例）
  - `check_platform_lock.sh` 平台铁律校验（扫描全部 .md，无友商平台提及才通过）
- 生成 Prompt：`prompts/` 存放可直接复用的生成提示词
  - `prompts/docx生成Prompt.md` — 产出 11 节《需求确认与方案设计表》
  - `prompts/html生成Prompt.md` — 产出可视化方案 HTML（A 营销式 / B 咨询诊断式）
